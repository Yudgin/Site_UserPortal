# Голосовой шлюз Binotel

Автоматический «секретарь» на внутренней линии облачной АТС Binotel. То, что 2026-10-16 проверили вручную
в консоли pjsua, здесь делается само:

1. Клиент звонит, сценарий Binotel отправляет звонок на линию **901**, где зарегистрирован шлюз.
2. Шлюз **отвечает** (200 OK — ранние медиа 183 Binotel клиенту не передаёт), включает приветствие,
   потом музыку/фразу ожидания по кругу.
3. Параллельно ищет клиента в Firestore (заявки, профиль, покупки корабликов — те же запросы, что у приёмника
   Binotel) и синтезирует голосом короткую **карточку** для менеджера, например
   «Дзвонить Петренко Іван. Ремонт номер 1234. Діагностовано. Runferry R3. Не крутиться правий гвинт.»
4. Через ~1 с после ответа звонит менеджеру на **907**. 503/408/480 до ответа — повторяет (до 2 раз через 1 с).
5. Менеджер снял трубку — слышит карточку. Через 0,7 с после неё (но не позже 20 с от начала карточки)
   шлюз делает **attended transfer**: REFER с Replaces на ноге клиента. Binotel соединяет клиента и менеджера
   напрямую, шлюз выходит из разговора.
6. Если что-то пошло не так:
   - перевод не удался → шлюз соединяет клиента и менеджера через себя (локальный мост, «bridged»;
     не дольше 60 мин — страховка, если BYE потерялся);
   - Binotel принял REFER (202/NOTIFY 100) и снял ногу менеджера, но итогового NOTIFY нет → это успешный
     Replaces, шлюз выходит из звонка (`connected_unconfirmed`), на запасную клиента не уводит;
   - менеджер не взял за 25 с, занят или положил трубку до перевода → слепой перевод клиента на **906**.
     Нет ни 202, ни NOTIFY за 8 с — шлюз кладёт клиента; REFER принят — ждёт, пока Binotel сам снимет ногу или
     пришлёт итог, до 90 с (итоговый NOTIFY может прийти только после ответа 906);
   - клиент положил трубку → шлюз кладёт менеджера.

Каждый звонок записывается одной строкой в локальный журнал.

## Состав

```
voice-gateway/
  engine/        SIP-движок на pjsua2 (C++): регистрация, звонки, проигрывание WAV, REFER. Команды/события — JSON-строки.
  brain/         логика на Node 24 (без своих npm-зависимостей)
    gateway.mjs  точка входа: запуск движка, логин линии, статус в консоль, Ctrl+C
    flow.mjs     сценарий одного звонка — чистая машина состояний (без I/O) + диспетчер событий
    card.mjs     текст карточки (из server/binotelWebhook.js: buildCustomerData, clientCategory, pickRequests)
    lookup.mjs   чтение Firestore (server/clientLookup.js), бюджет 1,2 с
    tts.mjs      синтез ElevenLabs → WAV 8 кГц, кэш по sha1(текста)
    gcp.mjs      токен Google (метаданные ВМ или gcloud) и Secret Manager
    journal.mjs  журнал data/calls-YYYY-MM-DD.jsonl
    storage.mjs  права 0700/0600, дневные логи с ротацией, удаление старых логов/карточек/журнала
    config.mjs   настройки по умолчанию + переменные VG_*
  data/          журнал и логи (в git не попадает)
  cache/         синтезированные карточки (в git не попадает)
```

Движок и логика общаются JSON-строками: команды в stdin движка (`register`, `local`, `answer`, `hangup`,
`play`, `stop`, `dial`, `xfer`, `xfer_replaces`, `bridge`, `quit`), события из stdout (`ready`, `reg`,
`incoming`, `untrusted`, `dialing`, `state`, `media`, `play_done`, `xfer`, `error`). Номера звонков — целые числа движка.
Сценарий звонка описан в начале `brain/flow.mjs`, команды — в `engine/engine.cpp`.

## Запуск на Mac

Нужно: pjproject 2.17 из Homebrew, Node 24, `gcloud` с входом `gcloud auth application-default login`
(для чтения Firestore и ключа ElevenLabs из Secret Manager), установленные зависимости `server/`
(`firebase-admin`, `express` — шлюз берёт их оттуда).

```sh
make -C voice-gateway/engine                # собрать движок → voice-gateway/engine/sip-engine
node voice-gateway/brain/gateway.mjs        # спросит SIP-сервер, логин и пароль линии (пароль не отображается)
```

Вместо ввода вручную учётку можно положить в Secret Manager (проект droidmaps-runferry) секретом-JSON
`{"server":"sip14.binotel.com","user":"<логин линии>","password":"<пароль>"}` и запустить
`BINOTEL_LINE_SECRET=<имя секрета> node voice-gateway/brain/gateway.mjs`. Логин и пароль линии — у владельца.

Остановка — **Ctrl+C**: шлюз снимает регистрацию, кладёт звонки и выходит (второй Ctrl+C — немедленно).

Если движок упал сам (не Ctrl+C), шлюз записывает незавершённые звонки как `aborted`, через 3 с запускает движок
заново и снова регистрирует линию. Живые разговоры при этом обрываются (BYE слать уже некому), а до новой
регистрации Binotel ещё до ~2 мин может слать вызовы на старый адрес. Падает чаще 5 раз за 10 мин — шлюз выходит
с кодом 1: тогда его должен поднять надзиратель (на ВМ — systemd, на Mac — launchd-агент с `KeepAlive`) или человек.

### Проверка без АТС (локально, с pjsua)

```sh
# менеджер: автоответ
pjsua --null-audio --no-tcp --local-port=5094 --rtp-port=42000 --id=sip:907@127.0.0.1:5094 --auto-answer=200
# шлюз: без регистрации, аккаунт sip:gw@127.0.0.1:5092
node voice-gateway/brain/gateway.mjs --local --manager sip:907@127.0.0.1:5094 --no-tts --no-lookup \
  --card /Users/yevhenyushchenko/Documents/GitHub/runferry-briefs/telephony/voice-prompts/wav-8k/mila/05-hold-short.wav
# клиент с разрешённого номера
pjsua --null-audio --no-tcp --local-port=5093 --rtp-port=41000 --id=sip:0500000001@127.0.0.1:5093 sip:gw@127.0.0.1:5092
```

2026-10-16 так прошёл весь сценарий: ответ, приветствие, карточка, REFER/Replaces, клиент и менеджер
соединились напрямую, в журнале `connected`.

### Автоматическая сквозная проверка: `voice-gateway/e2e-local.sh`

Собирает движок и сам прогоняет четыре сценария на 127.0.0.1 (шлюз :5092, клиент-pjsua :5091,
менеджер-pjsua :5093, консоли pjsua управляются файлами `tail -n0 -F <name>.ctl | pjsua …`):

| Сценарий | Что делает | Ожидаемый исход в журнале |
|---|---|---|
| s1 | менеджер с автоответом: приветствие → ожидание → карточка → REFER/Replaces | `connected`, клиент и менеджер говорят напрямую |
| s2 | менеджер не отвечает 4 с → слепой перевод на `sip:op@127.0.0.1:5093`, «оператор» берёт трубку из консоли | `fallback` (`manager_timeout`) |
| s3 | номер не из списка разрешённых | `rejected` (486), номер в журнале и консоли — только последние 4 цифры |
| s4 | менеджер отвечает 503 → 2 повтора набора через 1 с → запасная тоже 503 | `failed` (`manager_503`) |

Тестовый номер клиента 050 111 22 33 в список по умолчанию не входит — его пропускает только флаг `--allow`
этого прогона. Binotel, ElevenLabs и Firestore не нужны (`--no-tts --no-lookup --card`). Журналы — в
`voice-gateway/.e2e/<сценарий>/` (в git не попадают). Код выхода 0 — все проверки прошли. Скрипт можно запускать
повторно: в начале убирает остатки прошлого прогона, при выходе (и по Ctrl+C) — свои процессы.

### Флаги и переменные

| Флаг | Переменная | По умолчанию |
|---|---|---|
| `--manager 907\|URI` | `VG_MANAGER` | 907 → `sip:907@sip14.binotel.com;transport=udp` |
| `--fallback 906\|URI` | `VG_FALLBACK` | 906 (в `--local` = `--manager`) |
| `--allow +380…,…` | `VG_ALLOWED_CALLERS` | пусто — все внешние звонки получают «занято» (486) и идут дальше по сценарию Binotel; свой тестовый номер задавайте при запуске (плюс внутренние: 3-значный номер без `X-BINOTEL-GCID`) |
| | `VG_ALLOWED_INTERNAL` | пусто = все внутренние; `907,906` — только эти линии |
| | `VG_SIP_TRUST` | пусто: INVITE принимаются только с IP сервера Binotel (DNS + откуда пришёл 200 на REGISTER); список IP через запятую — добавить ещё адреса |
| `--no-tts` / `--no-lookup` | `VG_TTS=0` / `VG_LOOKUP=0` | синтез и поиск включены |
| `--card file.wav` | `VG_GENERIC_CARD_WAV` | нет (без синтеза — без карточки) |
| `--max-calls N` | `VG_MAX_CALLS` | 2 (каждый звонок — 2 ноги, лимит линии Binotel — 5) |
| `--server host` | `VG_SIP_SERVER` | sip14.binotel.com |
| `--engine path` | `VG_ENGINE` | voice-gateway/engine/sip-engine |
| | `VG_GREETING_WAV`, `VG_HOLD_WAV` | тестовые записи из runferry-briefs/telephony/voice-prompts/wav-8k/mila/ |
| | `VG_MANAGER_TIMEOUT_SEC`, `VG_DIAL_RETRIES`, `VG_CARD_MAX_SEC`, `VG_AFTER_CARD_MS` | 25, 2, 20, 700 |
| | `VG_XFER_TIMEOUT_MS`, `VG_FALLBACK_RING_SEC`, `VG_BRIDGE_MAX_MIN` | 8000 (нет ответа на REFER), 90 (REFER на 906 принят, ждём итог), 60 (предел моста) |
| | `VG_DATA_DIR`, `VG_CACHE_DIR` | voice-gateway/data, voice-gateway/cache |
| | `VG_LOG_DAYS`, `VG_CACHE_DAYS`, `VG_JOURNAL_DAYS` | 14, 30, 90 — сколько дней хранить логи, карточки, журнал (0 — не удалять) |
| | `VG_TRACE=1` | трасса команд/событий `data/logs/brain-*.log` (по умолчанию выключена) |

Все записи — WAV PCM 16 бит, моно, 8 кГц. Приветствие и ожидание сейчас — **внутренние тестовые тексты**;
клиентские тексты сначала согласуются по сегментам, аудио — только после утверждения.

## Безопасность

- **Только Binotel.** В реальном режиме движок принимает INVITE только с IP сервера линии (адреса из DNS и тот,
  откуда пришёл 200 на REGISTER; плюс `VG_SIP_TRUST`). С любого другого адреса (сканеры SIP, устройства в
  локальной сети) — 403 ещё до логики, в консоли одно предупреждение в минуту на адрес. Локальный режим
  (`--local`) слушает только 127.0.0.1 и адреса не проверяет.
- **Только разрешённые звонящие.** Номера не из `allowedCallers` (и не внутренние) шлюз не принимает — 486 Busy,
  без ответа. Внутренний — это 3-значный номер **без** `X-BINOTEL-GCID` (звонки из сценария, в том числе с
  короткими номерами операторов, Binotel помечает GCID); `VG_ALLOWED_INTERNAL` сужает до списка линий.
  Больше `--max-calls` одновременных — тоже 486.
- **В Firestore ничего не пишется.** Только чтение: `serviceRequests`, `clientProfiles`, `boatOrders` по номеру
  и `system/binotelRouting` для прогрева соединения при старте.
- **Журнал локальный**: `data/calls-YYYY-MM-DD.jsonl` (дата по Киеву). В строке: gcid, номер, категория клиента,
  id заявки, метки времени шагов (мс от входящего), наборы и повторы, коды, исход
  (`connected`, `connected_unconfirmed`, `bridged`, `fallback`, `fallback_unconfirmed`, `client_hangup`, `rejected`,
  `failed`, `aborted`), ошибки. Текста карточки и аудио в журнале нет. У отклонённых чужих номеров — только
  последние 4 цифры (и в журнале, и в консоли).
- **Секреты.** Пароль линии вводится скрыто или берётся из Secret Manager, уходит только в stdin движка;
  в консоль, журнал и логи не попадает (в трассе `data/logs/brain-*.log` поле заменено на `<…>`).
  Ключ ElevenLabs — только из Secret Manager `elevenlabs-api-key`, в логи не пишется.
- `cache/` содержит синтезированные карточки (имя клиента голосом) — локально, в git не попадает.
- Логи движка (pjsip) — `data/logs/engine-YYYY-MM-DD.log` (новый файл каждые сутки), в консоль не выводятся;
  номер звонящего там — только последние 4 цифры. Трасса команд/событий — только с `VG_TRACE=1`, входящие в ней
  без имени и URI, номер маской. При `SIP_ENGINE_LOG_LEVEL=4` в лог попадают **полные SIP-сообщения** —
  номера и имена клиентов, заголовки X-BINOTEL-*; значение `Authorization` и `nonce` движок заменяет на `<…>`,
  но такой лог всё равно не пересылать целиком.
- `data/`, `data/logs/`, `cache/` создаются с правами 0700, файлы — 0600. Старые файлы удаляются при запуске
  и раз в 6 ч: логи старше 14 дней, карточки — 30, журнал — 90 (`VG_LOG_DAYS`, `VG_CACHE_DAYS`, `VG_JOURNAL_DAYS`).
- В консоль не попадают управляющие символы из данных звонящего (имя в From и т. п.): они заменяются на `?`.

## Переезд на ВМ GCE (позже)

1. ВМ e2-small в европейском регионе (ближе к Binotel, например europe-central2), Ubuntu LTS, Node 24.
2. pjproject 2.17 собрать из исходников (Homebrew там нет) и поправить пути `PJ`/библиотек в `engine/Makefile`
   (на Linux вместо фреймворков macOS — `-lasound` или сборка без аудиоустройств, `--disable-video`).
3. Клонировать репозиторий, `cd server && npm ci --omit=dev` (шлюзу нужны `firebase-admin` и `express`).
4. Сервисный аккаунт ВМ: чтение Firestore (`roles/datastore.viewer`) и доступ к секретам
   `elevenlabs-api-key` и секрету линии (`roles/secretmanager.secretAccessor` на эти секреты).
   Токен шлюз сам берёт с сервера метаданных — `gcloud` на ВМ не нужен.
5. Записи приветствия/ожидания скопировать на ВМ и указать `VG_GREETING_WAV`, `VG_HOLD_WAV`.
6. Запуск как служба systemd: `BINOTEL_LINE_SECRET=<имя секрета> node voice-gateway/brain/gateway.mjs`,
   `Restart=on-failure`; остановка по SIGTERM снимает регистрацию. Единичные падения движка шлюз переживает сам
   (перезапуск через 3 с), systemd нужен на случай частых падений и падения самого шлюза.
7. Сеть: регистрация идёт изнутри (UDP 5060 на sip14.binotel.com), входящие порты для SIP не нужны.
   Для RTP проверить, что голос в обе стороны проходит через NAT GCE (у ВМ внешний IP 1:1); при проблемах —
   внешний IP в SDP или правило файрвола для UDP-портов RTP с адресов Binotel. Проверять на стенде.
